# 配信画面 (stage-web) の UX アップデート計画

> 起票: 2026-09-20。対象は `apps/stage-web` と、それが使う `packages/ui` のコンポーネント。
> admin-web と composer-template は、配信画面から見える範囲でのみ触れる。
>
> **この文書も腐る。** 行番号は起票時のもので、着手前にコードを確認すること。
> 「未確認」と書いた項目は実機で再現していない。
> 本文書の項目に着手したら、その場でここを直すか [`NEXT_WORK.md`](./NEXT_WORK.md) の D21 を更新する。

## 1. なぜ今これを書くか

stage-web は ADR 0014 で「配信中の全操作が 1 画面で完結する」画面として位置づけられた。
その後 ADR 0022 / 0025 / 0026 で投影、レイアウト、Egress の状態がサーバに移り、複数ウィンドウで巻き戻らない土台ができた。
いっぽう画面そのものは、機能が増えるたびに Card を足す形で育ってきた。
配信オペレーター (管理者とモデレーター) が本番中にどう動くか、という視点で全体を見直したことがない。

調査してみると、穴は「機能が足りない」より「あるはずの機能が画面に出ていない」に偏っていた。
ADR に書いてある権限が UI に無い、サーバが配っている状態を画面が読んでいない、ラベルどおりに動かないボタンがある、という種類である。
これは [`NEXT_WORK.md`](./NEXT_WORK.md) の X 節が指摘した「書いてあるが実装されていない」と同じ失敗クラスなので、先に潰す。

## 2. オペレーターの動線で見た現状

配信オペレーターの一日を 4 つの局面に分け、各局面で今できること、できないことを並べる。
ロールは DESIGN.md 4 章のとおり、管理者 (Cognito) とモデレーター (招待 URL) の 2 種類がオペレーターになりうる。

### 2.1 入室前 (配信サーバ起動から入室まで)

できること: 招待 URL を開くとトークンが自動入力され、マイクとカメラをプレビューで確認してから入室できる。
配信サーバが起動中なら `/join` の 503 を自動でリトライし、試行回数と待ち秒数をバナーで出す。

できないこと: **配信サーバが今どの段階か** (スタック作成中か、タスク起動中か、シグナリング応答待ちか) が分からない。
ADR 0023 と 0027 がこの情報を `provisioning` に書き戻しているが、表示先は admin-web の「配信インフラ」カードだけである。
モデレーターは admin-web に入れないので、リトライバナーの「起動待ち」以上のことを知る手段が無い。

### 2.2 配信開始 (入室から YouTube 送出開始まで)

できること: 管理者は Admin サブビューの `EgressControl` で送出を開始できる。
送出状態は room metadata で全ウィンドウに配られる (ADR 0026 D-2)。

できないこと:

- **モデレーターは送出を開始できない。** ADR 0026 D-3 は「開始・停止はモデレーターも操作できる」と決め、`stage-client.ts` にも `startEgress` / `stopEgress` がある。しかし `EgressControl` を描画しているのは Admin サブビュー (`App.tsx:1111`) だけで、Moderator サブビュー (`App.tsx:1230-1317`) には無い。
- **「LIVE」「ON AIR」が送出状態と無関係に点灯する。** ヘッダの pill (`App.tsx:921`) は再接続中でなければ常に LIVE、Admin プレビューの ON AIR (`App.tsx:1069`) と `PreviewWindow` の ON AIR (`PreviewWindow.tsx:56`) は無条件に出る。`egressActive` は metadata に乗っていて `applyRoomMetadata` (`App.tsx:197-212`) が読んでいるのに、`EgressControl` の状態にしか使われていない。登壇者は YouTube に出ているかどうかを画面から知れない。
- **管理者が「再試行」で繋ぎ直すと初期状態から始まる。** 初回接続 (`App.tsx:324`) と招待経路 (`App.tsx:356`) は接続直後に `applyRoomMetadata` を呼ぶが、Admin の再試行ボタン (`App.tsx:639-664`) は呼ばない。再試行で繋がった管理者はレイアウト grid、送出 idle の表示で始まる。

### 2.3 配信中 (送出開始から終了まで)

この局面が最も操作が多く、手を止められない。

できること: レイアウト切替、主役指定、PDF デッキの投影とページ送り、参加者のミュート要請、ステージへの上げ下げ、バナーと QR とオーバーレイの演出、チャット。
連打防止、再接続バナー、切断時の再入室導線は実装済み。

できないこと:

- **グローバルなキーボードショートカットが無い。** `apps/stage-web/src` に `keydown` の処理は 1 件も無い。矢印キーでのレイアウト循環は `LayoutPicker` にフォーカスがある時だけ効く。ページ送りもミュートもマウスでボタンを探す必要がある。
- **デッキ投影中はレイアウト選択が効かないのに、画面がそれを示さない。** composer は `slideUrl` があれば無条件に `SlideLayout` を描く (`Composer.tsx:311-317`)。stage-web の `LayoutPicker` はその間も普通に押せる。
- **管理者にデッキ操作とページ送りが無い。** Admin サブビューの ControlBar (`App.tsx:1052-1056`) はメディア制御と退室だけで、モデレーター向けの `deckControls` と `slidePageControls` を出していない。ADR 0025 D-3 で管理者はモデレーター相当の招待トークンを持っているので、API 側の制約は無い。
- **任意ページへ飛べない。** `slideGoTo` (`stage-controller.ts:214`) に UI が無い。モデレーターと登壇者に見えるのは `n / total` の数字だけで、今どのページが映っているかはプレビュー iframe 越しにしか分からない。
- **取り消せない操作に確認が無い。** 強制ミュート、プリセット削除、スライド投影の解除、登壇者をステージから下ろす、の 4 つは即時実行される。配信終了と Egress 停止には `AlertDialog` があるので、部品はある。
- **デッキのアップロード中はマイクもカメラも押せない。** `busy` が全操作で共有されている (`App.tsx:577-589` の `wrap`)。連打防止としては正しいが、数十秒かかるアップロードの間にミュートできないのは配信中には困る。
- **LiveStats の 5 指標中 3 つが常に「-」。** `App.tsx:1042-1045` が渡すのは参加者数と経過秒だけで、字幕遅延、ビットレート、ドロップフレームは `undefined` のままである。
- **字幕の状態が一切見えない。** 字幕は F-7 / F-8 / N-2 の主要機能で、イベント設定で ON にすれば CaptionWorker が起動する。しかし配信画面には字幕のプレビューも、動いているかどうかの表示も、言語の表示も無い。
- **エラーがレイアウトを押し下げる。** すべての通知がインラインの div で、`Toast` primitive は未使用である。プレビューの下に出るので、複数重なると操作部が下へずれる。

### 2.4 配信終了

できること: 管理者は `LifecycleControl` の「配信終了」を押せる。確認ダイアログは「LiveKit room を解散し、メディアスタックを破棄します。やり直しはできません」と告げる。

できないこと: **そのボタンは room から自分が抜けるだけで、API を 1 つも呼ばない。**

```ts
// App.tsx:1104-1109
onEnd={wrap(async () => {
  await controller.leave();
  setSession(undefined);
  setRoomState("stopped");
  clearInterval(elapsedRef.current);
})}
```

`stage-client.ts` にイベントの status を変える口は無い。
実際にスタックを破棄するのは admin-web で `ended` に遷移させたときだけである。
管理者が配信画面の「配信終了」を押して安心して帰ると、Fargate が翌朝まで動き続ける。
これは ADR 0026 が見つけた「Egress 開始ボタンがどの画面でも動いていなかった」と同じ形の欠落である。

## 3. アップデート項目

項目は 3 段に分ける。
Tier 0 は「ADR や画面の文言と実装がずれている」もので、設計判断は要らず、差分も小さい。
Tier 1 はオペレーターの手数を減らす改善で、既存の部品と API で組める。
Tier 2 は新しいデータ経路か画面構造の変更を伴い、着手前に ADR が要る。

各項目に「触る場所」と「想定の大きさ」を添える。
大きさは S (1 ファイル、半日以内)、M (数ファイル、1〜2 日)、L (backend を跨ぐ、ADR 込み) の 3 段階。

### Tier 0: 文言と実装のずれを直す

> ✅ **2026-09-24 に U-1a / U-2 / U-3 / U-4 / U-5 を実装** (PR #289)。
> `LifecycleControl` は使い手が無くなったので `packages/ui` から削除した。
> ロール別の描画は `apps/stage-web/src/App.test.tsx` (jsdom + フェイク) で固定している。
> 計画からの逸脱: U-1a の「admin-web への戻りリンク」は置いていない。stage-web は admin-web の
> URL を持っておらず、管理者は admin-web のボタンから新タブで来るので元のタブが残っている。
> 案内は文言だけにした。

#### U-1. 「配信終了」ボタンを文言どおりにするか、消す (S、判断 1 つ)

選択肢は 2 つある。

- **(a) 今すぐ**: ボタンを消すか「退室」に統合し、ダイアログの文言を「イベントの終了は管理画面から」に変える。admin-web への戻り導線 (リンク) を Admin サブビューのヘッダに置く。
- **(b) 本来の形**: 配信画面から `ended` へ遷移できるようにする。

(b) は一行では済まない。
管理者が stage-web で持っている資格情報は、LiveKit token と、ADR 0025 D-3 で同梱されたモデレーター相当の招待トークンだけである。
招待トークンでイベントを終了できるようにすると、モデレーターもスタックを破棄できることになり、DESIGN.md 4 章の権限表 (メディア層の起動と停止は配信管理者) を破る。
Cognito JWT を stage-web に渡す経路を作るか、管理者専用の短命トークンを別に発行するか、どちらにしても ADR が要る。

推奨は **(a) を先に入れて、(b) を Tier 2 の ADR 候補に送る**。
動かないボタンが「やり直しはできません」と脅している状態が一番悪い。
(2026-09-24 レビューで (a) に決定。)

触る場所: `App.tsx` の Admin サブビュー、`packages/ui/src/components/lifecycle-control.tsx`。

#### U-2. Moderator サブビューに `EgressControl` を出す (S)

Admin サブビューの `EgressControl` ブロック (`App.tsx:1111-1144`) をそのまま Moderator サブビューの右カラム上部に置く。
API もクライアントも既にモデレーターを通す (ADR 0026 D-3)。
`onStart` に確認ダイアログを付けるかは U-7 で扱う。

触る場所: `App.tsx` の Moderator サブビュー。

#### U-3. 「LIVE」「ON AIR」を `egressState` に連動させる (S)

ヘッダ pill、Admin プレビュー、`PreviewWindow` の 3 箇所の表示条件を `egressState === "active"` にする。
送出前は「PREVIEW」(緑、`preview-500`) を出し、送出中だけ赤の ON AIR にする。
ADR 0013 D-4 と 0029 D-1 の「赤はオンエアと破壊的操作だけ」に沿う。
`PreviewWindow` は `egressActive` を props で受ける。

副産物として、登壇者にも ON AIR が出る。
ADR 0026 の「影響」節が書いた「登壇者にも『ON AIR』を出せる」がこれで実現する。
`LiveTensionBar` の `tension` も同じ条件で `live` と `connecting` を分ける。
今は `connecting` と `ended` が一度も渡されない死にバリアントである (`App.tsx:591`)。

触る場所: `App.tsx`、`PreviewWindow.tsx`。

#### U-4. Admin の再試行経路で `applyRoomMetadata` を呼ぶ (S)

初回接続の後処理 (`App.tsx:320-330` 付近) を関数に切り出し、再試行ボタンからも呼ぶ。
プリセットとアセットの読み込みも初回だけなら、それも同じ関数に入れる。

触る場所: `App.tsx`。

#### U-5. `LiveStats` の未配線指標を消すか配線する (S)

字幕遅延、ビットレート、ドロップフレームは今のところ配信画面に届く経路が無い。
「-」が 3 つ並ぶ Card はオペレーターに「壊れている」と読まれる。
まずは参加者数と経過時間の 2 つだけの表示にし、指標が届く経路ができたら (U-13) 戻す。

経過時間の基点も直す。
今は管理ウィンドウを開いた時刻から数えている (`App.tsx:326`)。
`egressState` が `active` になった時刻から数えるか、`EventDefinition.egress` に開始時刻があればそれを使う。
オペレーターが知りたいのは「送出してから何分か」である。

触る場所: `App.tsx`、`packages/ui/src/components/live-stats.tsx`。

### Tier 1: 配信中の手数を減らす

#### U-6. グローバルキーボードショートカット (M)

配信中にマウスでボタンを探す時間を無くす。
`window` に `keydown` リスナーを 1 つ置き、次の条件で無視する。

- フォーカスが `input` / `textarea` / `contentEditable` にある (チャット入力中)
- `e.isComposing` が真 (日本語 IME の変換中。ここを見落とすと変換確定の Enter や Space が誤爆する)
- Ctrl / Alt / Meta 付き (ブラウザのショートカットと衝突させない)。Shift は `?` の入力に要るので許す

割り当ては最小限にする。

| キー     | 操作                              | ロール                       |
| -------- | --------------------------------- | ---------------------------- |
| `←` `→`  | スライドの前後 (デッキ投影中のみ) | 登壇者、モデレーター、管理者 |
| `1`〜`4` | レイアウト直接選択                | モデレーター、管理者         |
| `?`      | ショートカット一覧を Sheet で表示 | 全員                         |

各ボタンの Tooltip にキーを併記する。
`Space` は割り当てない。
ボタンにフォーカスがあるときの標準動作 (クリック) と衝突する。
マイクとカメラにも割り当てない (2026-09-24 レビューで決定)。
誤操作で配信中にマイクが切れる事故のほうが、ボタンを探す手間より大きい。

触る場所: `App.tsx` (フック 1 つ)、各ボタンの Tooltip。

#### U-7. 取り消せない操作に確認ダイアログを付ける (S)

強制ミュート、プリセット削除、スライド投影の解除、ステージから下ろす、Egress 開始の 5 つに `AlertDialog` を付ける。
既に `lifecycle-control.tsx` と `egress-control.tsx` で使っている部品をそのまま使う。

ただし、確認を増やすと手数が増える。
配信中に頻繁に使うもの (ステージから下ろす) は確認を付けず、代わりに直後 5 秒だけ「元に戻す」をバナーに出す方が良い。
どちらにするかは実装時に決めてよいが、強制ミュートとプリセット削除は確認必須とする。

触る場所: `participant-list.tsx`、`production-control.tsx`、`App.tsx`。

#### U-8. デッキ投影中のレイアウトロックを表示する (S)

`slideState.deckUrl` があるとき `LayoutPicker` を `disabled` にし、Card のヘッダに「スライド投影中はレイアウトが固定されます。解除すると戻ります」を出す。
composer の動作 (`Composer.tsx:311-317`) は変えない。
composer 側を変えて「スライドと登壇者を並べる」レイアウトを増やすのは、別の機能要望として扱う。

触る場所: `App.tsx` の `layoutPicker`。

#### U-9. Admin サブビューにデッキ操作とページ送りを出す (S)

`deckControls` と `slidePageControls` を Admin の ControlBar にも並べる。
`inviteToken` が無い旧 Lambda の場合 (`lib/token.ts:26-29`) は、既存のエラー文言「配信操作の資格情報がありません」で弾かれるので追加の分岐は要らない。

触る場所: `App.tsx` の Admin サブビュー。

#### U-10. `busy` をメディア制御とそれ以外で分ける (S)

`busy` を 2 つに分ける。
`busy` は API を伴う操作 (アップロード、送出開始、レイアウト保存) の連打防止に残す。
マイクとカメラと画面共有のトグルは LiveKit のローカル操作なので、`busy` に関係なく押せるようにし、トグル自身の二重押しは `pending` フラグで防ぐ。

触る場所: `App.tsx` の `wrap` と `mediaControls`。

#### U-11. 入室前に配信サーバの段階を見せる (M、backend を少し触る)

`/join` が 503 を返すとき、`reason: "media-unavailable"` だけでなく `provisioning` の `phase` と `services` の進捗を一緒に返す。
サーバは `EventDefinition.provisioning` を既に持っている (ADR 0023 D-3)。
stage-web の `ReconnectingBanner kind="retry-progress"` に「SFU 起動中 (0/1)、字幕 1/1」のように出す。

これで、モデレーターが admin-web を見られなくても「あと何を待っているか」が分かる。
`phase === "failed"` のときはリトライを止め、`signalingError` の内容と「管理者に連絡してください」を出す。
今は失敗していても 60 秒間リトライし続ける。

触る場所: `services/control-api/src/usecases/join.ts`、`packages/shared` の `JoinResponse`、`App.tsx`、`reconnecting-banner.tsx`。

#### U-12. 通知を Toast に寄せる (S)

エラーとミュート通知を `Toast` primitive に移し、プレビューの下から画面の右上へ動かす。
再接続バナーは、画面全体に関わる状態なのでインラインのまま残す。
`role="alert"` と自動消去の挙動は今のまま引き継ぐ。

触る場所: `App.tsx` の `statusBanners`。

### Tier 2: 新しい経路や画面構造 (ADR が先)

#### U-13. 字幕の状態と最新テキストを配信画面に出す (L、ADR 0030)

配信画面に字幕が一切見えないのは、データ経路が無いからである。
CaptionWorker は字幕イベントを YouTube と独自 API と S3 に流すが、LiveKit room には流していない。

ADR で決めることは 3 つある。

- **経路**: LiveKit の DataChannel に `caption` メッセージを足すか、LiveKit の Transcription API を使うか、control-api 経由でポーリングするか。DataChannel なら composer にも届き、将来 YouTube 以外に焼き込み字幕を出す道も開ける
- **見せるもの**: 最新 1〜2 行のプレビュー、エンジンの生存 (最終イベントからの経過秒)、遅延 (`captionLagMs`)。言語切替やエンジン切替は配信中にやらない (DESIGN.md 2.3 のとおり YouTube は 1 言語)
- **誰に見せるか**: オペレーターだけか、登壇者にも出すか

UI は `LiveStats` の隣に「字幕」Card を 1 つ置く形で済む。
U-5 で消した字幕遅延の指標をここで戻す。

#### U-14. 配信画面からイベントを終了する (L、ADR、U-1 の続き)

U-1 (b) の本来の形。
管理者専用の資格情報を stage-web に渡す設計を ADR にする。
候補は、`issueStageToken` が admin 専用の短命トークン (`role: admin`、有効期限 6 時間) を追加で同梱し、`POST /stage/lifecycle/end` をそのトークンだけで通す形である。
モデレーターの招待トークンでは通らないようにする。

#### U-15. スライドのサムネイル一覧と任意ページジャンプ (M)

`pdf.js` は既に stage-web に入っている (`lib/pdf-pages.ts`)。
モデレーターのコントロールタブに、現在ページの前後 2 枚ずつのサムネイルを横に並べ、クリックで `slideGoTo` を呼ぶ。
全ページのグリッドは Sheet で開く。
サムネイルはアップロード時にクライアントで生成し、メモリに持つだけで永続化しない (ADR 0022 D-3 のサーバ側ラスタライズ不採用に沿う)。

登壇者にはサムネイルを出さない。
登壇者は `deckUrl` を受け取らない (`App.tsx:489-491`) ので、出そうとすると権限設計から変わる。

#### U-16. 狭い画面での縦積み (M)

`ResizablePanelGroup` が常に横 65/35 で、縦積みへのフォールバックが無い。
タブレットや半画面で開いたとき右カラムのフォームが読めなくなると考えられる (未確認、実機で再現していない)。
`md` 未満で `orientation="vertical"` に切り替え、`ChatPanel` の固定 px 高さ (`chat-panel.tsx:77`) を親に追従させる。

配信オペレーターがモバイルで運用する想定は DESIGN.md に無い。
優先度は低く、実機で困った人が出てから着手でよい。

## 4. やらないこと

既存の ADR で決まっているものは、この計画で再検討しない。

- **配信画面のライトテーマ**: ADR 0013 D-5 でダーク固定。登壇者ブースで眩しくないため
- **チャットの永続化**: ADR 0020 D-4 でメモリのみ。再入室で消えるのは仕様
- **RTMP URL の表示**: ADR 0026 補足で招待トークン経路には返さない。ストリームキーが漏れる
- **サーバ側の PDF ラスタライズ**: ADR 0022 D-3 で不採用
- **composer のレイアウト追加** (スライドと登壇者の並置など): 合成側の機能要望として別に起票する

## 5. 着手順

Tier 0 を 1 つの PR にまとめる (U-1a、U-2、U-3、U-4、U-5)。
どれも `App.tsx` の差分が中心で、互いに依存しない。
この PR だけで、文言と実装のずれと「見えない状態」の大半が消える。

Tier 1 は U-6 (ショートカット) と U-11 (起動段階の表示) を先にする。
どちらも本番中と本番直前の不安を直接減らす。
残り (U-7 から U-10、U-12) は思い出したときに 1 つずつ PR を切る。

Tier 2 は ADR 0030 (字幕の配信画面への経路) から始める (2026-09-24 レビューで決定)。
U-14 は U-1a が入っていれば急がない。

## 6. 検証の方針

Tier 0 と Tier 1 は `App.tsx` の描画分岐が中心なので、`stage-controller.test.ts` の流儀 (フェイクの `RoomConnector`) でロール別の描画を単体テストに足す。
特に U-3 は「`egressActive: false` の metadata で ON AIR が出ない」を必ずテストに残す。
`e2e/` の Playwright は R7 (統合テスト CI) と一緒に整えるので、この計画では当てにしない。
