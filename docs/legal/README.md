## 公開前に決めること (2026-09-17 の実装突合で判明)

テンプレートの記述と実装を突き合わせたところ、**12 件の不一致**が見つかりました。
文面だけで直せるものは修正済みです。以下は**運用判断が要るもの**で、
**期間を決めて実装にも反映してから**公開してください。

実装が決めていない期間を規約に書くと、守れない約束になります。

### 1. イベント申請フォームの氏名・連絡先 (最優先)

`POST /event-requests` は**認証を要しません**。申請者は本サービスのアカウントを持たない
第三者でありうるのに、氏名と連絡先が **DynamoDB に無期限で保存**されます。TTL がありません。

- 決めること: 保管期間 (例: 申請から 1 年、または対応完了から 90 日)
- 実装: `EventRequest` に TTL 属性を足し、テーブルの `timeToLiveAttribute` を設定する

### 2. 録画ファイルの保管期間

- 現状: **無期限**。30 日で低頻度アクセス、90 日で Glacier に移行するだけで、消えません
- 決めること: 何日で削除するか。そもそも削除するか
- 実装: `infra/lib/control-plane-stack.ts` の `archive-recordings` ルールに `expiration` を足す

**あわせて**: 90 日で Glacier に移行しますが、**復元処理が未実装**なのでその後はダウンロードが
失敗します。長期保管した録画を提供する運用にするなら、復元の実装か Glacier 移行の削除が要ります。

### 3. 字幕ファイル (SRT/VTT) の保管期間

- 現状: **無期限**。ライフサイクルルールがありません
- 決めること・実装: 録画と同様

### 4. CloudWatch Logs の保管期間

- 現状: メディア層 1 週間 / 調整ループ 1 ヶ月 / **その他の Lambda は無期限**
- 決めること: 全体で揃えるか
- 実装: 各 Lambda の `logRetention` を指定する

### 5. アラームの通知先 (公開運用に移すときに設定する)

```ts
// infra/user-config.ts
budgetEmail: "ops@example.com",  // 月額 50 USD の 80% / 100% 通知
opsEmail: "ops@example.com",     // スタックが立たない等の運用アラーム
```

**開発中は意図的に未設定** (2026-09-17 の判断)。手元で見ているのでメール通知の価値が薄い。
購読者ゼロは設定漏れではないので、**発見しても報告不要**。

公開運用に移すとき、とくに**自分が見ていない時間に配信が走る**ようになったら設定すること。
`budgetEmail` のほうは、終了操作を忘れたイベントの Fargate が回り続ける事故に効く。

### 6.

同意 UI を入れるか (NEXT_WORK L1 の積み残し)

招待 URL から入る登壇者・モデレーターに、入室前の同意取得画面を出すかどうか。
現状は「利用者は録画されることに同意したものとみなす」(利用規約 第6条3) で済ませています。

## 実装済みで、規約に反映済みのもの

- 登壇資料と翻訳用語集は**イベント終了時に自動削除**されます (PR #240/#241)
- S3 の旧バージョンは削除から **7 日**で完全に消えます (PR #248)。
  それ以前は削除マーカーが付くだけで実体が残っていました
- DynamoDB は **Point-in-Time Recovery が有効**で、削除後 **35 日**は復元可能です
- **IP アドレス・User-Agent は収集していません**。Cookie も使っていません
- Bedrock は**米国リージョン**で処理されます (越境移転の記載を追加済み)
